# 极端视野临时表面内存修复

编辑器允许 `view_blocks_h=2`。在逻辑画布 1600×900 下，分块会尝试缩放到 14400×14400，一次请求 829,440,000 字节；视野 4 也请求约 207 MB。原有 64MiB 限制在分配后才决定是否缓存，不能防止申请本身造成卡顿或内存耗尽。

审计用实际 `World.draw` 和 pygame 缩放入口，超过 64MiB 时拦截，不真的创建巨型表面。修复前报告的数值是实际分配请求，不是进程峰值 RSS。

现在先估算分配；超预算时只绘制可见部分。`chunk_scaling.py` 用一维采样条取得 pygame 最近邻索引，按相同索引将不透明原生像素绘制到可见矩形，不创建完整巨型目标。采样条 LRU 同时限制 4MiB/32 项；更大的程序化缩放按可见坐标直接计算，避免把大申请转移到采样条。离屏分块也在创建/缩放前跳过。

| 合法视野 | 修复前最大请求 | 修复后最大请求 | 修复后绘制 |
|---|---:|---:|---|
| 2 | 829,440,000 字节，已拦截 | 57,600 字节 | 正常完成 |
| 4 | 207,388,800 字节，已拦截 | 28,804 字节 | 正常完成 |

修复后对应场景约 5～6ms，时间受本机负载影响。完整原始数据为 `evidence/2026-11-11_zoom_allocations_before.json` / `..._after.json`；旧版固定为 `e1ec7ec`，可重复安全拦截：

```bash
python scripts/audit_zoom_allocations.py --legacy --output /tmp/zoom-before.json
python scripts/audit_zoom_allocations.py --output /tmp/zoom-after.json
```
