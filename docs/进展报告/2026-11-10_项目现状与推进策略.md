# Pixel Roamer 项目现状与推进策略

- 调研日期：2026-11-10
- 范围：当前 `main` 工作树中的代码、地图、配置、提交记录及可运行检查
- 目的：解释项目当前可用状态，识别优先处理的故障，并给出分阶段推进方案

## 执行摘要

项目已经形成一套内容丰富的单机 2D 平台探索游戏原型：包含页面流程、地图选择与编辑、网格世界、角色物理、方块交互、buff、时装、音频及 12 张地图。地图生成、世界绘制和基础物理可以通过本次无窗口检查。

目前不能认为游戏可正常交付。无窗口启动在加载页首帧即崩溃；有限复活次数的死亡流程也无法按配置工作。这些基础缺陷与缺少依赖声明、自动化回归测试同时存在，足以解释“很多功能看似已实现、实际使用无效或异常”的现状。建议先建立可启动、可重复验证的基线，再按核心游玩闭环修复和验收，最后扩展内容。

## 项目组成与现状

### 架构概览

- `main.py` 集中管理页面状态、输入事件、玩家控制、胜负状态、HUD 和渲染输出，是主要集成点。
- `world.py` 管理地图格子、实体碰撞索引、分块缓存和绘制；`camera.py` 负责跟随及坐标变换。
- `creature.py` 实现玩家物理、伤害、攀爬/游泳接触、拾取和状态效果。
- `block_types_*.py`、`buff_system.py`/`buff_data.py`、`costumes.py`、`sfx.py`/`music.py` 分别承载内容定义、buff、时装及音频。
- `maps/` 以每张地图一个 Python 模块的方式定义地图，部分地图另有 `config.json`。地图覆盖探索、循环世界、收集目标和限时玩法等类型。

### 项目管理现状

- README 只有项目简介，没有安装、启动、操作、排障说明。
- 仓库没有 `requirements.txt`、`pyproject.toml` 等依赖声明，也未发现测试目录或 CI 配置。
- 开发、玩法和展示逻辑大量汇集在 `main.py`，跨系统改动难以隔离验证。
- 地图主要由 Python 代码生成，缺少可自动检查的地图契约和玩法验收记录。

### 已确认问题

#### P0：启动页必现崩溃

`loading_screen.run_loading_screen()` 在第 248 行执行 `_status_timer += dt`，但函数没有将 `_status_timer` 声明为 `global`。因为函数中还会给该变量赋值，Python 将其视为局部变量，首帧读取时触发 `UnboundLocalError`。`_status_index` 同样在函数中读写，却没有声明为全局变量；修正计时器后也会触发同类错误。`init_loading_screen()` 对状态变量的赋值也没有声明相应全局变量，因此初始化值没有写回模块状态。

复现命令：

```bash
SDL_VIDEODRIVER=dummy SDL_AUDIODRIVER=dummy python main.py
```

实际栈顶为 `main.py:3026` 调用加载页，然后在 `loading_screen.py:248` 失败。该问题阻断所有正常启动路径。

#### P0：配置的有限复活次数不会生效

`Player.on_death()`（`creature.py:1201-1206`）调用 `reset()`，而 `reset()` 会立刻将 `alive` 设回 `True`（`creature.py:1120-1127`）。因此 `main.py:2582` 检查死亡状态的逻辑通常看不到死亡状态。该分支内部也没有扣减 `_player_lives_left` 的代码。结果是配置了有限命数的地图会在死亡后直接复位，命数不减，也不会因耗尽命数进入失败状态。

这影响配置为有限命数的探索地图（如冒险湾、终焉神殿、宏大旅程），属于玩法规则失效，不只是显示问题。

#### P1：启动流程与可测试性不足

- 当前启动错误没有测试捕获，表明页面模块没有最小初始化/渲染回归检查。
- `main.py` 在模块顶层创建窗口并进入无限游戏循环，不适合被普通测试直接导入；页面逻辑也不易独立调用。
- 依赖未声明，干净环境无法直接运行；本次系统 Python 缺少 Pygame，必须临时补齐后才可执行运行检查。
- 音频依赖 SDL 设备，图形逻辑需区分离屏烟测与真实窗口、键盘和音频设备验收。

## 推进策略（按优先级）

### P0：恢复基础可运行性与建立质量门槛

1. 修复加载页状态变量作用域问题，为加载页增加初始化和连续多帧渲染回归检查。
2. 重构死亡/复活流程，让死亡信号、重置位置、无敌时间和命数扣减顺序明确；覆盖有限命数和无限复活两种配置。
3. 声明并锁定运行依赖，记录受支持的 Python/Pygame 版本、安装和启动步骤。
4. 添加最小自动化门槛：语法编译、模块导入、启动页渲染、地图加载/边界契约、关键死亡状态转换。
5. 每次修复都附可重复的回归步骤，避免依赖“运行起来看着正常”的主观判断。

**验收标准：**干净环境可按文档启动；加载页可运行到主页；有限命数耗尽进入失败，无限复活持续可玩；自动化检查能在修改后重复通过。

### P1：验证核心游玩闭环，修复跨系统失效

按玩家实际路径逐项验收并自动化可确定性行为：地图选择与返回、水平移动/跳跃/落地、固体/单向平台碰撞、伤害/护盾/治疗、死亡与重生、体力与攀爬、游泳与上岸、拾取与计分、方块特殊效果、终点通关、计时结束、暂停/设置返回、配置保存再加载。

地图按玩法类型分组，至少为每类选择代表地图；对其他地图运行统一契约检查（合法方块 ID、出生点、模式参数、终点/得分目标、边界行为）。游戏内可编辑属性需验证“编辑—保存—重新加载—实际生效”的完整链路。

**验收标准：**每项规则均有明确输入、预期状态和回归用例；代表地图的完整通关/失败路径由人工实机验收并记录设备与版本。

### P2：降低维护成本并恢复内容迭代

1. 将页面/输入状态、游戏规则与绘制逐步从 `main.py` 拆成可单独验证的模块。
2. 统一地图配置 schema，添加范围校验和错误提示，避免编辑器写入不可运行参数。
3. 建立版本说明、已知问题和每张地图的验收清单；明确正式地图与测试地图。
4. 在质量门槛稳定后，再增加地图、buff、方块及特效内容。

**验收标准：**新地图可以按模板实现并通过自动契约检查；变更影响范围可追踪，发布版本有可回归的验收记录。

## 2026-11-10 第二轮动态审计与性能优化

在 SDL dummy、Pygame 2.6.1、Python 3.10.12 环境下，增加了冷启动地图列表、代表地图首绘/热绘、角色更新、音乐合成及全地图页面导航的耗时测量。第二轮主要发现和修复：

- `list_maps()` 原先导入所有地图模块并触发生成；改为缓存读取 `MAP_ID` 和静态地图摘要。地图列表冷耗时由 **2.06 秒**降到 **0.032 秒**，查询尺寸/模式/循环信息不再生成地图。
- 世界首次绘制原先预渲染全图；改为只绘制可见 chunk，并用 LRU 限制基础纹理和缩放纹理缓存。像素启程首绘由 **1.16 秒**降至 **41 毫秒**，宏大旅程由 **6.41 秒**降至 **110 毫秒**。缩放纹理缓存限制为 64 MiB。
- 微型世界的 1×1 双循环世界在超大视口下原先每帧绘制数百万重复 chunk，首帧约 **20.0 秒**、热帧约 **15.2 秒**；不可分辨的空循环世界现在直接填充默认色，首帧和热帧均约 **0.8 毫秒**，且不分配 chunk 缓存。
- 宏大旅程原先创建完整 6000×150 地形后再清除大部分方块；改为只生成最终保留的地表和顶部边界。生成耗时由 **1.94 秒**降至 **0.32 秒**，最终方块数仍为 **140,372**，终点仍存在。
- 首次音乐合成原先通过后台 Python 线程争用 GIL；改为主循环按每帧约 4 毫秒预算分片推进。全地图页面导航的总耗时由约 **4.39 秒**降至 **1.95 秒**，测得最大帧间隔由 **1.26 秒**降至 **443 毫秒**。最大间隔出现在选择大型地图时，剩余耗时主要来自该地图的单次生成和首绘。
- 普通测试地图 1 的物理/碰撞更新为 **0.053 毫秒/帧**；主页 60 帧均值约 **5.2 毫秒/帧**，没有显示出优先级高于地图生成/首绘的瓶颈。

第二轮复测：7 项自动回归全部通过，包含全地图元数据与实例一致性、选择单张地图不导入其他地图、首绘性能门槛、终点触发、积分目标、有限/无限复活、移动/碰撞/跳跃、加载页、音乐分片和无窗口启动；`compileall` 与 `git diff --check` 通过。全部 12 张地图仍可经页面流程逐张启动并返回。

当前仍有两类待实机验证项：真实桌面窗口下的音频/输入/长时间运行；大型地图首次选择时约数百毫秒的生成和首绘延迟。后者已从多秒降到亚秒，之后可考虑加载进度提示或进一步拆分地图生成阶段。
